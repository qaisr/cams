# /jira-enhance — Feature C (batched enhancement, A + B)

## Input

`$ARGUMENTS` — `[KEY, …]` (comma/space-separated), or empty to derive a scope (e.g. current sprint /
an epic subtree via `_index.json`). If a scope is derived, confirm the resolved key list with the
human before proceeding.

Requires `jira/.manifest.json`. If absent → tell the user to run `/jira-init` and STOP.

## What this writes (only after per-ticket Apply)

| Path | When |
|---|---|
| `specs/.push-runs/<run_id>.json` | at batch start (created if `specs/.push-runs/` is absent), updated per ticket |
| `jira/<type>/{KEY}.md` + `.json` | per applied A-edit / B-create (via `/jira-add-issue` Step-4 gate) |
| `jira/.manifest.json` | item pointers; B-create intent records |
| `jira/_index.json` | regenerated by `/jira reindex` after the batch (derived) |
| `specs/<name>/jira-mapping.json` | per ticket that traces to a spec |

**Never** edits `specs/` requirement docs. **Never** auto-applies.

## Engine

Feature C is a **batch driver** over the shared pipeline — it adds no engine step. Each proposed
change re-enters `.claude/commands/jira-write-engine.md` as either an **A-edit** (Feature A path) or a
**B-create** (Feature B path). Feature C owns only: batch framing, per-ticket gating, terminal-state
safety, the run-manifest, and the single consolidated suggestion.

### Step C0 — Resolve batch + terminal-state safety

1. Resolve the key list (from `$ARGUMENTS` or the derived scope).
2. **Skip Done/Closed** (per `statusCategory` map in `jira-sync.config.yml`) **unless the key was
   explicitly named** in `$ARGUMENTS`. Report each skipped terminal ticket.
3. Open the **run-manifest** `specs/.push-runs/<run_id>.json` (create `specs/.push-runs/` if absent).
   `run_id` = a timestamped id. Seed it with `{ run_id, startedAt, keys: [...], results: [] }`.

### Step C1 — Per-ticket gap analysis + decomposition

For each non-skipped key, in order:
1. **Whole-picture context.** If the ticket traces to a spec/epic via `specs/sources/manifest.json`,
   align suggestions to that spec's language + DoD; otherwise stay ticket-local. (`jira-helper`'s gap
   analysis is the natural upstream, but C re-checks itself.)
2. Produce proposed enhancements and **decompose** each into:
   - **A-edit** → description/AC change on this key → enter the Feature A path (Step 1 diff over the
     pushable slice).
   - **B-create** → a child task (e.g. a testing sub-task) under this key as parent → enter the
     Feature B path (draft + intent record).

### Step C2 — Drive each change through the shared engine (per-ticket gate)

For each decomposed change, run `jira-write-engine.md` Steps 2–8, but **gate per ticket**:
- **Step 3 APPROVE is the strictest gate** — per ticket [Apply / Reject / Edit] via `AskUserQuestion`.
  Record the decision in the run-manifest `results[]` (`{ key, kind: "A-edit"|"B-create", decision,
  outcome, realKey?, error? }`).
- **Step 4 RE-CHECK per ticket** — the lost-update version guard for A-edits; the intent-record
  re-check for B-creates. A remote advance STOPs *that ticket only* (3-way shown), the batch continues.
- **Steps 5–7** exactly as the engine defines (mutate → re-pull → reconcile via `/jira-add-issue`
  gate). Update the ticket's run-manifest entry with its outcome + any real key.
- **Do NOT run Step 8 per ticket.**

### Step C3 — Batch close

1. Run **`/jira reindex`** once after the batch to regenerate `_index.json`.
2. Finalize `specs/.push-runs/<run_id>.json` (`finishedAt`, per-key outcomes — the audit/rollback
   record; only a batch has rollback-worthy blast radius).
3. **Step 8 SUGGEST — once, consolidated.** Collect the distinct specs touched (via
   `specs/sources/manifest.json`; skip silently if absent) and print **one** `/reconcile-requirements`
   suggestion covering the whole batch. **Never auto-run.**
4. Print a summary table: `KEY · kind · decision · outcome (+ realKey for creates)` and the
   run-manifest path.

## Guardrails

- **Never auto-apply** — per-ticket [Apply / Reject / Edit] is the strictest gate in the engine.
- **Skip Done/Closed** unless the key is explicitly named.
- **Per-ticket lost-update guard** — a remote version advance STOPs that ticket (3-way), batch
  continues; no clobber.
- **Run-manifest is mandatory** — every key + outcome recorded for audit/rollback before the batch
  closes.
- **One consolidated reconcile suggestion** — printed once, never auto-run (R3). Never edits `specs/`
  docs.
- **Reuse, don't duplicate** — A-edits and B-creates route through the exact Feature A / Feature B
  engine paths; local writes go through `/jira-add-issue`; rollup through `/jira reindex`.
- **No secrets** — MCP brokers auth; cloudId is the pinned `CONNECTION` value.
